No. The checked-in source supports an intended asynchronous registration-to-notification flow, not proof that every successful request delivers exactly one email. Most decisively, `SendRegistrationEmailConsumer.Consume` only logs a notification and returns `Task.CompletedTask`; it contains no email-provider call or delivery acknowledgment (`src/Sample.Components/Consumers/SendRegistrationEmailConsumer.cs:18–23`).

The supported source-level chain is:

- The POST controller awaits `SubmitRegistration` and returns HTTP OK with registration fields. It does not await downstream notification processing (`src/Sample.Api/Controllers/RegistrationController.cs:19–35`). The service creates a registration, calls `Publish(new RegistrationSubmitted ...)`, awaits `SaveChangesAsync`, and then returns (`src/Sample.Components/RegistrationService.cs:21–52`). Thus the success path establishes completion of those awaited operations, not email delivery.
- API configuration registers `IRegistrationService` as `RegistrationService`, configures PostgreSQL, and enables the EF bus outbox and RabbitMQ (`src/Sample.Api/Program.cs:30–46,73–87`). The database model includes inbox/outbox entities (`src/Sample.Components/RegistrationDbContext.cs:23–31`). These are configuration and model declarations, not observations of committed rows or broker delivery.
- The saga correlates `RegistrationSubmitted` by registration ID. Its initial handler copies registration fields, transitions to `Registered`, and publishes `SendRegistrationEmail`. It then deliberately throws on the first attempt when payment is below 50, before publishing `AddEventAttendee` (`src/Sample.Components/StateMachines/RegistrationStateMachine.cs:14–40`). Its definition configures retries and an EF outbox (`src/Sample.Components/StateMachines/RegistrationStateDefinition.cs:9–14`). The worker registers the saga and email consumer and configures RabbitMQ endpoints (`src/Sample.Worker/Program.cs:74–88`). This establishes intended wiring, not actual activation or execution counts.

“Exactly one” is unsupported even if “email” is interpreted as processing the notification message. A unique member/event registration index (`src/Sample.Components/RegistrationDbContext.cs:47–51`) does not establish uniqueness of an external email side effect. The worker configures a 30-second duplicate-detection window (`src/Sample.Worker/Program.cs:65–70`); this is not evidence of unlimited end-to-end deduplication. Nor does the intentional failure prove duplicate delivery: the configured outbox/retry behavior must be distinguished from observed execution.

There is also a concrete durability concern in this sample: the API registers a database-recreation hosted service (`src/Sample.Api/Program.cs:48`), whose startup calls `EnsureDeletedAsync` followed by `EnsureCreatedAsync` (`src/Sample.Api/RecreateDatabaseHostedService.cs:22–35`). If executed against the relevant database, this would remove persisted state, including pending outbox data. I did not observe a restart or actual data loss.

Missing evidence includes an actual email-sending implementation and its delivery semantics; the deployed build/configuration and active endpoints; correlated HTTP, transaction, outbox, broker, saga, and consumer records; and provider/recipient delivery evidence. An exactly-once claim additionally needs a demonstrated idempotency/atomicity mechanism covering the external email effect, plus evidence for crash, retry, redelivery, outage, and restart cases. The retrieved source supplies no observed runtime delivery evidence, and finite happy-path traces alone would not establish the universal claim.
